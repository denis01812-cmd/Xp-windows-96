# Как устроен XP / 96

## Не приложение, а загружаемый образ

`build/xp96.img` — сырой образ виртуального IDE-диска. В нём собственные загрузчик и машинный код ядра, без Linux, Python-интерпретатора или JavaScript. Python работает только на компьютере разработчика. HTML/CSS/JS нужны лишь для необязательной страницы с эмулятором.

```text
BIOS
 └─ boot/boot.S        16-битный первый сектор
     └─ boot/loader.S  BIOS EDD, загрузка ядра, VBE, A20 и GDT
         └─ kernel/entry.S   32-битный вход, очистка BSS
             └─ kernel/main.cpp
                 ├─ COM1 / IDT / PIC / PIT / PS/2
                 ├─ графический буфер и рабочий стол
                 └─ цикл: опрос ввода → перерисовка при изменениях → HLT
```

## Диск

Сектор имеет размер 512 байт. Размер образа — 2 МиБ.

| LBA | Содержимое |
|---|---|
| 0 | Первый загрузчик, ровно 512 байт, подпись `55 AA` |
| 1–8 | Второй загрузчик с нулевым дополнением до 4096 байт |
| 9 и далее | `kernel.bin`, количество секторов задаётся при сборке |

Загрузка использует BIOS Extended Disk Drive Services (`INT 13h`, `AH=42h`). Это IDE-образ для BIOS, не загрузочная дискета, не ISO, не UEFI-образ и не раздел FAT.

Текущий второй загрузчик читает ядро за один BIOS-вызов. Поэтому лимит двоичного ядра — **127 секторов / 65 024 байта**. Проверки есть и в Python, и в линкерном скрипте. Перед добавлением крупных ресурсов потребуется изменить загрузчик, а не просто увеличить константу.

## Карта памяти

| Адрес | Назначение |
|---|---|
| `0x5000` | Структура `BootInfo`: видеобуфер, pitch, разрешение, глубина и позиции RGB |
| `0x5200` | Временный блок информации VBE от BIOS |
| `0x7C00` | Первый загрузочный сектор |
| `0x8000` | Второй загрузчик |
| `0x10000` | Точка входа и загружаемые секции ядра |
| `0x90000` | Начало стека, стек растёт вниз |
| `0x100000` | Начало BSS: программные видеобуферы и состояние |
| Адрес из VBE | Линейный видеобуфер устройства |

Используется плоская адресация без paging, пользовательского режима, динамической кучи и планировщика процессов. Окна — части одного ядра, а не изолированные программы. Поддерживаемая конфигурация эмулятора — **64 МиБ RAM**; определения карты RAM через E820 пока нет.

## Процессор, таймер и ввод

- GDT содержит нулевой, кодовый и информационный дескрипторы с плоскими 32-битными сегментами.
- IDT перехватывает исключения общим обработчиком остановки. Отдельного диагностического отчёта по каждому вектору пока нет.
- PIC переназначается на векторы `0x20` / `0x28`; аппаратно разрешён только IRQ0.
- PIT выдаёт IRQ0 примерно 100 раз в секунду. Обработчик увеличивает счётчик и отправляет EOI.
- Клавиатура и мышь PS/2 опрашиваются в основном цикле; их IRQ отключены в контроллере.
- Клавиатура использует перевод в scan code set 1 и раскладку US; мышь — обычные трёхбайтовые пакеты.
- Лог COM1: 115200 бод, 8N1. Маркеры `XP96:BOOT`, `XP96:INPUT_READY`, `XP96:DESKTOP_READY` используются тестами.

Ядро останавливает процессор через `HLT` между событиями; IRQ таймера будит его для следующего опроса.

## Графика и окна

Загрузчик запрашивает VBE-режим `0x115`: 800 × 600, true color, линейный буфер. Он проверяет атрибуты и RGB-маски. Ядро поддерживает 24- и 32-битный вывод с учётом pitch и смещений каналов.

`graphics.cpp` рисует в собственный 32-битный буфер. При публикации кадра пиксели переводятся в формат VBE. Процедурные обои сохраняются отдельно и повторно не вычисляются на каждом кадре.

`desktop.cpp` содержит фиксированное число окон и их Z-порядок. Перерисовка происходит при вводе или смене секунды. Здесь нет аппаратного ускорения, композитинга с альфа-каналом, resize окон или отдельных процессов.

## Файлы и заметки

`WELCOME.TXT` и `SYSTEM.TXT` — встроенные тексты. `NOTES.TXT` показывает ограниченный буфер заметок в RAM. Никакого чтения каталогов основного компьютера или сохранения на его диск нет. После загрузки ядра ОС вообще не пишет в виртуальный IDE-диск.

Терминал также встроен в ядро: команды вызывают функции C++, а не запускают EXE. Буферы ввода, заметок и истории имеют фиксированные размеры.

## Инструменты и тесты

- `tools/build.py`: GNU GCC/G++, ассемблер через GCC, GNU LD и Objcopy; стандартной библиотеки Python достаточно. Можно переопределить `CC`, `CXX`, `LD`, `OBJCOPY`.
- `tools/run.py`: пересборка и запуск QEMU. `QEMU` может указывать путь к исполняемому файлу.
- `Start-XP96.bat` и `tools/run-windows.ps1`: запуск готового образа на Windows без компилятора, Python или WSL; поиск QEMU, проверка загрузочной подписи, TCG, snapshot и отключённая сеть гостя. Рабочая папка передаётся отдельно от относительного ASCII-имени образа: это обходит разницу UTF-16/UTF-8/ANSI в аргументах Windows-сборок QEMU. Для пользовательского Unicode-имени файла создаётся временная ASCII-именованная копия с очисткой после выхода; исходный образ не меняется.
- `tools/package_windows.py`: проверка размера и SHA256 по манифесту, упаковка образа, запускателя и инструкции; сторонние EXE не включаются.
- `tools/fetch_bios.py`: загрузка фиксированной версии SeaBIOS для v86 с проверкой SHA256; это не часть `xp96.img`.
- `tools/preview.py`: HTTP-сервер с явным списком публичных маршрутов, без доступа ко всему репозиторию.
- `tests/test_build.py`: границы, выравнивание, детерминированность упаковки, ELF и HTTP-маршруты.
- `tests/test_windows_package.py`: комплектация Windows-архива, SHA256, загрузочная подпись, CRLF и BOM для PowerShell.
- `tests/windows-launcher.ps1`: Windows CI вызывает настоящий `.bat` / PowerShell с тестовым EXE вместо QEMU, проверяет пути, обнаружение QEMU и обработку ошибок. Он проверяет также реальное открытие относительного образа из рабочей папки, ASCII-only аргумент диска и очистку временной копии, но сам не эмулирует CPU.
- `tests/windows-qemu.ps1`: настоящая загрузка пакета в нативном Windows QEMU до `XP96:DESKTOP_READY`, в том числе из Unicode-каталога и с Unicode-именем образа и `TEMP`. В CI используется фиксированный установщик QEMU с SHA256 из WinGet-манифеста; двоичные файлы QEMU в артефакты проекта не включаются.
- `tests/boot.mjs`: настоящая загрузка образа в v86, проверки видеопамяти, синтетический ввод PS/2 и повторная загрузка. Скриншот снимается из framebuffer эмулятора, а не рисуется отдельно.

Для одной версии GNU-инструментов сборка повторяема: в образ не добавляются текущее время или случайные значения. Разные версии компилятора могут создать другой машинный код и SHA256.
